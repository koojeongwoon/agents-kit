> 이번 필수 구현에서 제외하며, 구현 순서·보장 범위는 새 계획을 따른다.

- 작성일: 2026-09-23
- 상태: 검토안 — 구현 착수 및 ADR 채택 전
- 대상: [엔터프라이즈 보안 설계](../architecture/enterprise-security-and-gateway.md), [ADR-010](../decisions/ADR-010-endpoint-security-daemon-and-gateway-defense.md)
- 용도: 기능별 실현 가능성·우선순위·기대효과를 평가하고 단계별 착수 기준을 정한다.

## 1. 제품 방향과 첫 고객 가설

대상 단말은 **회사 지급 PC와 업무에 사용하는 개인 소유 PC 모두**다(사용자 확인). 회사 업무에 사용하는 기기는 Agent Kit 설치·조직 등록을 필수 조건으로 둔다. 원격 작업환경으로 일괄 전환하는 것을 기본 전제로 삼지 않는다. OS, MDM 등록, 직원의 관리자 권한, 보안 정책 변경 권한은 아직 확인되지 않았다.

기업 사용의 기술적 조건은 설치·등록에 더해 필요한 관리 권한 확보와 정책 적용 검증까지 포함하도록 설계한다. 회사는 기준을 충족한 기기만 보호 대상 회사 자원에 접근하도록 한다. 소유권과 무관하게 검증되지 않은 기기는 허용 상태로 표시하지 않는다. 설치 의무 자체가 관리자 우회 방지나 단말 무결성의 증명은 아니다.

Agent Kit은 여러 AI 클라이언트에 회사가 승인한 설정과 도구 연결을 안전하게 배포하고 유지한다. Tools Gateway는 회사 자원에 대한 도구 호출을 서버에서 인가하고 감사한다. 두 제품을 함께 사용하면 개발자는 도구를 쉽게 설정하고, 운영자는 누가 어떤 정책으로 자원에 접근했는지 확인할 수 있다.

핵심 위협은 직원이나 에이전트가 비인가 MCP를 업무용 PC에 추가해 로컬 회사 자료를 읽거나 외부로 전송하는 것이다. 정상 권한으로 내려받은 회사 코드도 보호 대상이며, Gateway를 거치지 않는 로컬 도구 경로를 첫 검증에 포함한다.

첫 고객은 여러 AI 개발 도구와 사내 API를 함께 사용하는 개발팀·플랫폼팀으로 가정한다. 첫 구매 가설은 **업무용 PC에서 비인가 MCP 사용 제한, 승인된 도구의 쉬운 배포, 회사 자원 접근의 중앙 통제**다. 시장 수요와 지불 의사는 아직 검증하지 않았다. 보안팀과 개발팀을 함께 파일럿에 참여시켜 효과를 확인해야 한다.

Agent Kit의 Configuration & Distribution Plane은 독립적으로 사용할 수 있어야 한다. 기업 연동 기능은 선택 모듈로 제공한다. 초기 `agentkitd`는 조직의 승인된 도구 정책 적용·검증·감사를 맡는다. 실행 제한은 클라이언트 공식 관리 기능과 회사의 OS 보안 통제에 연결하며, 자체 에이전트 루프는 후속 선택 모듈로 유지한다.

### 보안 실현 가능성 판단

**판정: 추진할 수 있다.** 설치·조직 등록을 업무 사용 조건으로 강제하고 필요한 정책 적용 권한을 확보한다면, 승인된 AI 도구 배포·비인가 MCP 사용 제한·기기 상태에 따른 회사 접근 제한을 결합한 보안 제품은 구현 경로가 있다. 기존 Agent Kit의 설정 배포 구조를 활용할 수 있지만, 보호된 정책 적용 서비스와 클라이언트/OS 통제 연동은 신규 개발·검증이 필요하다. 모든 기능을 일반 파일 감시 데몬 하나로 달성하는 설계는 수정해야 한다.

아래는 설치 의무가 있는 업무용 단말을 기준으로 한 판단이다. '가능'은 구현 방법이 있다는 의미이며 현재 제품의 구현 완료를 뜻하지 않는다. 대상 OS와 클라이언트는 아직 확정하지 않았다.

| 시크릿/개인정보 전송 탐지와 마스킹 | 제한된 경로에서 가능 | 관리된 요청·응답의 필드 단위 검사로 알려진 민감정보 노출 감소 | 오탐·누락·인코딩·스트리밍 검증. 포괄적 유출 방지로 약속하지 않음 / P2 |
| 모든 AI 프롬프트 유출·인젝션의 완전 차단 | 현재 보장 불가 | 권한 제한과 탐지 보조로 피해 범위 축소 | 전체 전송 경로·문맥 파악에 한계. 연구 기능으로 유지 / P3 |

**가장 큰 기술 위험은 허용된 범용 인터프리터와 개발 편의성의 양립이다.** MCP라는 이름이나 네트워크 포트만 검사해서는 임의 프로그램의 행동을 통제할 수 없다. 사용자가 쓸 수 있는 Python·Node·shell을 통해 동일한 파일 읽기와 외부 전송을 수행할 수 있으므로, 프로그램의 승인 여부와 실제 자원 접근 권한을 함께 다뤄야 한다. 개발자의 정상적인 빌드·테스트까지 대량 차단하면 운영 가능한 제품으로 평가하지 않는다.

권장 구현 분담은 Agent Kit이 승인 도구 카탈로그·정책 변환·적용·진단을 담당하고, `agentkitd`가 보호된 정책 적용과 실행 경계 연동을 맡으며, 클라이언트 공식 관리 기능과 OS/기존 단말 보안 기능이 실제 강제를 담당하는 것이다. Gateway는 서버의 독립적인 인가와 회사 접근 조건을 담당한다. OS마다 강제 기능이 다르므로 첫 OS의 검증 결과를 다른 OS에 그대로 적용하지 않는다.

**현재 코드의 선행 보완:** `gui/server/app.js`의 `/api/session`은 로컬 요청에 mutation token을 반환한다. 이 구조를 그대로 관리자 권한 데몬에 연결하면 승인되지 않은 로컬 프로세스가 관리 기능을 호출할 수 있는 경로가 생긴다. 기존 GUI는 일반 사용자 권한에 두고, 데몬은 호출자 확인뿐 아니라 조직 정책 출처·요청 작업·허용 대상까지 검증해야 한다. 같은 사용자로 동작하는 악성 MCP가 얻을 수 있는 UI 토큰만으로 정책 변경을 허용하지 않는다. 현재 구성 서비스 자체의 취약점 확정이 아니라, 더 강한 권한을 부여할 때 반드시 변경해야 할 신뢰 경계다.

첫 성공 판정은 **정상 개발 작업과 승인 MCP는 동작하고, 비인가 MCP·정책 변경·인터프리터 우회·범위 밖 파일 접근·허용 밖 외부 전송·미등록 기기의 서버 접근이 정의된 경계에서 거부되는가**다. 서버 차단만 통과하거나 파일 감시 알림만 동작하는 결과로 단말 보안 게이트를 통과시키지 않는다.

## 2. 평가 기준과 근거 수준

### 실현 가능성

- **높음**: 통제하는 구성 요소 안에서 구현 경로가 명확하다. 구현 완료를 뜻하지 않는다.
- **조건부**: 클라이언트 공식 기능, OS 권한, 실행 경로 또는 서버 계약을 먼저 검증해야 한다.
- **연구 필요**: 범용 보장을 위한 근거가 부족하다. 제한된 실험으로 적용 범위를 찾아야 한다.

### 우선순위

- **P0 — 첫 제품 증명**: 보안 경계를 정하고 두 제품의 연결 가치를 입증하는 필수 기능.
- **P1 — 기업 파일럿**: 운영 가능한 설치·정책·감사·승인 체계를 완성한다.
- **P2 — 검증 후 확장**: P0/P1 효과를 확인하고 실제 고객 요구가 있을 때 추가한다.
- **P3 — 연구 또는 보류**: 불확실성과 유지비가 크므로 초기 제품 약속에 넣지 않는다.

예상 부담의 소·중·대는 구현, 운영, 호환성 유지 비용을 합친 상대 평가다. 인력·일정 견적은 아니다. 기대효과도 검증 전 가설이며 매출·보안 성능 수치를 단정하지 않는다.

이번 평가는 Agent Kit 문서와 관련 소스의 정적 확인에 근거한다. Gateway·IAM·Credential Broker의 현재 구현·배포 상태와 클라이언트별 실제 차단 동작은 이번 평가에서 검증하지 않았다. 아래 서버 기능은 요구 계약으로 읽는다.

## 3. 제품별 책임과 보장 범위

| 구성 요소 | 책임 | 보장 범위 및 전제 |
|---|---|---|
| Agent Kit CLI / GUI | Manifest, 카탈로그, 지원 여부, 배포 계획·Diff·병합·검증·롤백 | 기존 공통 application service를 사용하며 소유권을 확인한 설정만 변경 |
| `agentkitd` | 승인된 MCP 정책 적용·검증, 설정 변경 감지, 상태·감사 전송 | GUI와 권한 분리. 보호된 관리 경로로 정책 적용. 시스템 변경 권한은 필요한 작업에 한정하며 로컬 관리자의 우회 가능성을 검증 |
| 클라이언트의 관리 기능 / OS 통제 | 승인된 MCP만 사용하도록 강제, 정책·서비스 보호, 실행·네트워크 제한 | 회사 관리 권한과 기존 MDM/단말 보안 제품을 연동. 제품·버전별 강제 범위를 검증하며 Agent Kit이 범용 OS 보안 엔진을 새로 구현하지 않음 |
| Tools Gateway | 매 호출의 사용자·테넌트·도구·자원·행위 인가, 제한, 감사, 접근 회수 | Gateway를 통과하는 호출과 Gateway 권한으로 접근하는 자원에 적용 |
| IAM / Credential Broker | IAM은 사용자·기기 신원과 기기 등록·회수의 기준, Broker는 외부 자격 증명을 사용하는 서버 측 실행 | IAM 기기 등록 기능은 신규 구현이 필요. 사용자·테넌트 소유 외부 자격 증명은 Broker 안에서 사용하고 결과만 반환하는 계약을 요구 |
| 정책 관리 기능 | 정책 승인·버전·배포·회수 | 초기에는 Gateway 제품의 관리 모듈 후보. 서명 키와 관리 권한은 일반 도구 실행 권한과 분리 |

Gateway는 로컬 데몬의 허용 판정을 그대로 신뢰하지 않는다. 사용자 토큰과 단말 등록 증명을 구분하고, 단말 상태 보고를 단말 무결성의 증명으로 간주하지 않는다. mTLS를 사용하더라도 사용자·테넌트·도구 인가를 별도로 수행한다.

외부 모델로 보내는 프롬프트, 클라이언트 내장 shell, 개인 자격 증명으로 직접 실행하는 API, 일반 브라우저는 Gateway 통과 여부를 별도로 확인해야 한다. 이 경로까지 강제하려면 검증된 클라이언트 관리 기능과 OS/네트워크 통제가 필요하다.

로컬 도구에 대해서는 세 가지를 구분해 검증한다: (1) 관리 대상 클라이언트에서 비인가 MCP 사용 차단, (2) 다른 클라이언트·shell·인터프리터를 통한 실행 우회 제한, (3) 승인된 도구의 파일 접근과 외부 전송 제한. (1)의 성공으로 (2)와 (3)을 완료 처리하지 않는다. 회사 소유라는 사실만으로 세 가지가 강제된다고 가정하지 않는다.

### 업무용 기기의 등록과 접근 조건

1. Agent Kit을 설치하고 사용자·조직·기기를 연결해 등록한다. 사용자 인증만으로 기기 등록을 대체하지 않는다.
2. 승인된 MCP 정책과 필요한 클라이언트/OS 통제를 적용하고 실제 동작을 검증한다. 개인 소유 PC에도 업무 사용에 필요한 관리 범위를 명시한다.
3. 서버가 등록·회수 상태와 정해진 신뢰 수준의 정책 적용 증거·유효 기간을 확인한 경우에만 보호 대상 접근을 허용한다. `installed=true`나 데몬 heartbeat만으로 준수 상태를 판정하지 않는다.
4. 미등록·회수·정책 미충족·상태 유효 기간 만료 시 신규 접근과 갱신을 거부한다. 종료·삭제된 데몬은 다음 검증 또는 상태 만료 시 감지될 수 있으므로 차단 지연 상한을 정하고 시험한다.
5. Gateway 외 회사 코드 저장소·직접 API·VPN 등 보호 대상 진입점도 동일한 기기 조건을 적용하거나 우회 경로를 닫는다. Gateway 연동만 완료한 상태를 회사 전체 접근 통제로 표시하지 않는다.

등록 해제는 향후 서버 접근을 차단할 수 있지만 이미 로컬에 내려받은 회사 자료의 사용을 자동으로 막지는 않는다. 해당 자료를 보호할 클라이언트·OS 통제의 지속성은 별도 시험한다. 개인 소유 기기에 필요한 관리 범위를 적용할 수 없으면 업무용 기기 등록을 완료 처리하지 않는다.

### 기대효과에 따른 투자 판단

- **초기 효과와 확실성이 큼**: F01~F04, F06~F07. 기존 설정 배포 자산과 Gateway 통제를 연결해 고객이 바로 확인할 수 있는 결과를 만든다.
- **초기 가치 성립의 필수 조건**: F05/F08의 최소 등록·정책 신뢰 경로와 F10. 업무에 사용하는 회사 지급·개인 소유 PC에서 비인가 MCP 차단 및 미충족 기기의 회사 자원 접근 제한을 P0에 검증한다. 성공이 불확실하다는 이유로 핵심 요구를 후순위로 옮기지 않는다.
- **기업 운영을 위해 필요**: F05, F08~F09, F11~F12, F16, F20의 P1 범위. 파일럿 운영자가 관리 가능한 제품을 만든다.
- **고객 요구와 실험 결과로 투자 결정**: F13, F17~F18. 제품 가치가 있지만 전제와 유지비가 크다.
- **초기 차별점으로 약속하지 않음**: F14~F15, F19. 성공 가능성을 범위가 제한된 실험으로 먼저 확인한다.

## 5. 단계별 진행 계획과 완료 기준

### 단계 0 — 범위·계약 확정과 가능성 검증

업무용 등록 정책을 적용한 테스트 PC에서 OS 1개, 클라이언트 1개, 승인된 로컬 MCP 1개와 비인가 MCP 시험용 대체물, 원격 읽기 전용 도구 1개를 선정한다. 회사 지급·개인 소유 각각에 요구할 관리 조건을 정의하고 해당 권한 구성에서 시험한다. 테스트 자료와 통제된 수신지만 사용한다. 현재 개발 환경을 고려한 OS 후보는 macOS이며, 고객 환경 확인 전 확정하지 않는다. 클라이언트는 공식 관리 기능과 실제 설치 버전을 확인한 후 고른다.

산출물과 완료 기준:

1. 기능별로 `설정 배포 가능 / 변경 감지 가능 / 실행 강제 가능 / 관찰 불가`와 OS·버전·공식 근거·실험 결과를 기록한다. 미지원·미검증도 명시한다.
2. 사용자 실수, 악성 로컬 도구, 일반 사용자 우회, 로컬 관리자 침해를 구분한 위협 모델을 작성한다. 업무 사용 기기의 MDM·관리자 권한·정책 보호 상태를 확인하고 필요한 관리 조건을 정한다. 설치·등록·준수 판정·상태 만료·접근 거부 계약과 Gateway 외 보호 대상 진입점을 정의한다.
3. Gateway·IAM·Broker 현재 소스와 API를 확인해 기존 기능 재사용·수정·신규 개발을 판정한다. Agent Kit에서 세 제품의 책임을 중복 구현하지 않는다.
4. 정상 호출, 미허용 자원 접근에 더해 비인가 로컬/원격 MCP 추가, 사용자·프로젝트·실행 옵션의 정책 우회, 허용 이름을 이용한 명령·URL 교체, 데몬 중지, 다른 클라이언트·shell 실행, 로컬 시험 자료의 외부 전송을 검증한다. 클라이언트 강제와 OS 강제를 각각 기록한다.
5. 데몬 IPC의 호출자 권한, 정책 출처, 업데이트 신뢰, 자격 증명 저장, 로그 수집 범위를 설계한다. 기존 단일 사용자 GUI의 신뢰 모델을 자동 승계하지 않는다.
6. 허용한 Python·Node·shell을 통한 우회와 승인 MCP의 범위 밖 파일 접근·외부 전송을 시험한다. 정상 빌드·테스트·도구 호출도 함께 검증해 개발 업무와 통제가 양립하는지 판정한다.

**다음 단계 조건:** 선정한 클라이언트의 비인가 MCP 사용 차단이 재현되고, 실행 우회·로컬 자료 접근·외부 전송의 잔여 경로와 필요한 OS 통제가 명확해야 한다. 필요한 강제가 불가능하면 대상 클라이언트나 단말 관리 조건을 재검토한다. 감지·알림만 성공한 결과로 차단 요구를 충족했다고 판정하지 않는다.

### 단계 1 — P0 단말 차단과 Gateway 연결 증명

F01~F08, F10의 P0 범위를 구현한다. 데몬은 단일 OS에서 조직 정책의 적용·검증·변경 감지·상태 보고를 수행한다. 조직 정책을 보호할 설치 권한과 기존 단말 관리 연동은 이 단계의 필수 조건이며 F20의 배포 자동화까지 미루지 않는다. 원격 MCP 요청은 클라이언트가 Gateway에 직접 보내고, 데몬은 IAM에 기기를 등록·증명하며 Gateway에는 정책 상태·로컬 이벤트를 보낸다. 기기별 원격 호출 차단은 직접 요청과 IAM 등록 기기의 검증 가능한 결합을 확인한 후에만 완료 처리한다.

완료 기준:

- CLI와 GUI에서 동일한 계획·배포·검증·롤백 결과를 얻는다. 사용자 소유 설정이 보존된다.
- 읽기 전용 허용 요청은 성공하고, 금지 자원·쓰기·잘못된 사용자/테넌트 요청은 Gateway에서 거부된다.
- 승인된 로컬 MCP는 동작하고 비인가 MCP는 관리 대상 클라이언트에서 로컬/원격 모두 사용되지 않는다. 사용자·프로젝트 설정이나 실행 옵션으로 제한을 넓힐 수 없어야 한다.
- 승인된 도구의 허용 파일·네트워크 범위 밖 작업은 거부되고 정상 빌드·테스트는 유지된다. 일반 로컬 프로세스나 악성 MCP가 GUI 토큰을 얻더라도 조직 정책을 변경하거나 데몬에 임의 권한 작업을 시킬 수 없어야 한다.
- 로컬 자료 접근·외부 전송을 포함한 단계 0의 우회 시험을 반복한다. 관리 정책 변경·서비스 중지 시 보호 상태와 처리 결과를 기록한다. 전체 단말 차단을 주장하려면 OS가 담당하는 우회 제한도 통과해야 한다.
- 설정 변경을 감지해 보호 상태가 달라졌음을 표시한다. 데몬 중지 시 정상 보호 상태로 계속 표시하지 않는다.
- 세션 권한 회수 후 신규 호출이 거부되는 시간을 측정하고, 캐시·네트워크 조건을 기록한다.
- 미설치·미등록·회수·정책 미충족 기기의 관리 채널 요청을 거부한다. 원격 MCP 접근의 기기별 거부는 직접 요청과 기기의 결합이 입증된 경우에만 완료 처리한다. 사용자 토큰만 다른 기기로 옮긴 우회, 가짜 상태 보고, 데몬 중지·제거 후 차단 지연을 시험하고 기기 신뢰 증거의 한계를 명시한다.
- 배포와 도구 호출을 감사 이벤트로 연결할 수 있으며 테스트 시크릿이 Manifest·계획·응답·감사 로그에 노출되지 않는다.

### 단계 2 — P1 기업 파일럿

P0의 단말 등록·회수를 대규모 운영으로 확장하고, 서명 정책의 키 교체·배포 운영, 내구성 있는 감사 큐, 호출 제한, 예외 승인, 단일 OS 설치·업데이트·제거를 완성한다. 조직 관리 필드 자동 복구는 먼저 알림 모드로 관찰한 뒤 선택적으로 활성화한다.

완료 기준:

- 등록되지 않거나 회수된 단말의 단말 제한 대상 호출을 거부한다. 단말 상태 자기 보고의 한계를 표시한다.
- 정책 변조·만료·구버전 재생·잘못된 테넌트 정책을 거부하고 키 교체를 검증한다.
- 정책 서버 단절 시 마지막 검증 정책의 유효 기간과 기능별 처리 기준이 정해져 있다. 유효한 인가를 확인할 수 없는 보호 대상 호출은 거부한다.
- 감사 재전송의 누락·중복, 디스크 포화, 재시작을 시험한다. 감사가 필수인 호출의 큐 포화 시 처리 기준을 정한다.
- 승인 인수 변경·만료·재사용을 거부한다. 설치·업데이트 실패에서 복구하며 불필요한 관리자 권한을 요구하지 않는다.
- 실제 운영자가 차단 이유, 정책 버전, 단말 상태, 승인 이력을 확인할 수 있다.

### 단계 3 — P2 선택 확장

파일럿 요구에 따라 승인된 로컬 MCP의 추가 지원, 제한된 DLP, SIEM/WORM, 추가 OS·클라이언트, 브라우저, 모바일 승인을 각각 선택한다. 한 기능의 성과를 다음 확장의 조건으로 삼는다.

DLP는 대표 업무와 공격 예제에서 탐지 누락·오탐·지연을 측정한다. 브라우저는 인증 세션 격리와 실제 네트워크 경계를 검증한다. 지원하는 경로만 제품에 표시한다.

### 단계 4 — P3 별도 검토

전체 프롬프트 DLP, 문맥 탐지, 모바일 원격 실행은 별도 실험 및 투자 판단을 거친다. 자체 Harness가 필요하면 ADR-009에 따라 실행 격리·자격 증명·취소 경계를 먼저 충족한다.

## 6. 효과 측정과 진행 중단 기준

| 평가 항목 | 수집할 지표 | 판단 방식 |
|---|---|---|
| 도입 편의 | 신규 사용자 설정 완료 시간, 수동 수정 횟수 | 파일럿 시작 전 기존 방식과 비교 |
| 배포 안정성 | 배포 성공률, 사용자 설정 손실, 복구 성공률 | 사용자 소유 설정 손실이나 복구 실패가 있으면 확장 전 수정 |
| 정책 가시성 | 변경 감지 지연, 정상 변경 오경보, 상태가 오래된 단말 비율 | 정상 업무를 방해하지 않는지 확인 |
| 접근 통제 | 사전에 정의한 허용·거부·우회 시나리오 결과 | 허용되지 않은 서버 자원 접근이 성공하면 게이트 실패 |
| 비인가 MCP 차단 | 로컬/원격 등록·사용, 정책 변경, shell 우회, 시험 자료 접근·전송 결과 | 관리 대상 MCP 차단에 실패하면 P0 실패. OS 우회 제한이 미검증이면 전체 단말 통제를 주장하지 않음 |
| 사고 대응 | 신규 호출 거부까지 걸리는 시간, 진행 중 작업 처리 결과 | 측정 조건과 p50/p95를 보고하고 서비스 목표는 실측 후 확정 |
| 감사 신뢰성 | 서버 수신 확인, 누락·중복, 재전송 지연, 민감값 노출 | 데이터 손실·민감값 노출 원인을 해결한 뒤 확장 |
| 운영 비용 | 단말당 장애·문의 수, 업데이트 실패율, 승인 대기 시간 | 절약한 설정 시간과 추가 운영 부담을 함께 비교 |
| 수요 | 개발자 지속 사용, 운영자 활용, 도입 의사 | 가치가 확인되지 않으면 브라우저·모바일·고급 탐지 투자를 보류 |

실측 전에는 ROI, 탐지율, 0.1초 회수, 수 ms DLP 지연을 제품 성능으로 표시하지 않는다. 원본 프롬프트·소스·스크린샷을 감사 기본값으로 수집하지 않고, 메타데이터와 민감값을 제거한 결과를 우선한다.

## 7. 사전 준비와 결정이 필요한 사항

### 사전 준비

- 현재 배포 서비스의 안전성·소유권·회귀 테스트 상태를 확인한다. [기존 보안 백로그](../handoff/security-remediation-backlog.md)의 미구현 표기를 그대로 재사용하지 않는다. 현재 `lib/security-boundary.js`와 `bin/cli.js`에는 공통 self-target 보호 호출이 존재하며, 이번 평가에서는 테스트를 실행하지 않았다.
- Gateway/IAM/Broker 계약 및 테스트 환경을 확보하고, 테스트 사용자·권한·읽기 전용 자원을 준비한다.
- 클라이언트 공식 관리 기능과 버전별 근거를 수집한다. 기존 매핑 표의 경로를 보안 강제의 증거로 사용하지 않는다.
- 단말 설치 권한, 키 보관, 배포 서명, 서버 감사 저장소의 운영 책임자를 정한다.

### 결정이 필요한 사항

| 결정 | 권장 초안 | 결정하지 않을 경우 영향 |
|---|---|---|
| 첫 고객·OS·클라이언트 | 개발팀 파일럿, OS 1개·클라이언트 1개 | 호환성 범위와 일정 산정 불가 |
| 조직 관리 수준 | 회사 지급·개인 소유 모두 설치·등록 필수. MDM·관리자 권한·관리 범위와 정책·실행·네트워크 통제 조건을 P0에서 확정 | 비인가 MCP 차단과 업무 사용 조건의 전제가 성립하지 않을 수 있음 |
| 기기 접근 조건 | 검증된 기기 등록·정책 상태와 유효 기간을 서버 인가에 결합하고 Gateway 외 진입점도 목록화 | 설치 확인만으로 접근을 허용하거나 직접 접근 우회가 남음 |
| 데몬 권한 | GUI와 보호된 정책 적용 서비스를 분리하고 시스템 권한은 필수 작업에 한정 | 일반 사용자 서비스만으로 조직 정책 보호를 보장하거나 불필요한 권한을 확대할 위험 |
| 오프라인 정책 | 일반 설정 작업은 로컬 제공, 보호 대상 실행은 유효한 인가가 있어야 허용 | 장애 때 보안과 업무 지속 기준 불명확 |
| 정책 관리자·예외 승인자 | 조직/테넌트 범위 역할, 만료·사유·감사 필수 | 개발자나 모델이 정책을 스스로 넓힐 위험 |
| 감사 범위·보관 | 메타데이터 우선, 기간·접근 권한 명시 | 민감정보 수집과 저장 비용 확대 |

이 문서는 권장 초안을 제공한다. 결정 전에도 단계 0의 읽기 전용 조사와 제한된 가능성 검증은 진행할 수 있지만, 미결 사항을 제품 보장으로 확정하지 않는다.

## 8. 원안에서 조정할 표현과 근거

| 원안 표현 | 평가 후 적용할 표현 |
|---|---|
| 모든 로컬 도구와 프롬프트를 데몬에서 차단·검사 | 검증된 관리 경로만 통제, 나머지 경로는 감지 가능 여부 명시 |
| 설정 무단 변경 시 즉시 롤백 | 변경 감지 후 조직 관리 필드에 한해 승인된 복구 계획 적용 |
| 서명된 도구만 실행 | 배포물 출처 검증과 실제 실행 경로 통제를 별도 검증 |
| 로컬 해시체인으로 위변조 방지 | 중앙 수신 확인·외부 체크포인트와 결합한 변경/누락 탐지. 침해 단말의 로그 완전성 보장 불가 |
| 0.1초 킬 스위치 | 신규 호출 거부 지연을 측정. 로컬 프로세스 종료·진행 중 호출·외부 부작용은 별도 계약 |
| 무결점 거버넌스 / 탈옥 방어 | 인가·자원 제한·감사와 평가된 범위의 탐지 보조 |
| 생체인증으로 1초 2FA 승인 | 검증된 추가 인증과 정확한 작업에 결합된 승인 |

참고한 공식 자료(2026-09-23 확인):

- [Claude Code 설정 및 우선순위](https://code.claude.com/docs/en/settings): 일반 사용자/프로젝트 설정과 조직 관리 설정은 별도 경로다. 이 사실은 관리 기능 조사 근거이며 모든 클라이언트의 강제 가능성을 뜻하지 않는다.
- [Claude Code 조직 MCP 통제](https://code.claude.com/docs/en/managed-mcp): 관리 MCP 구성과 허용 목록으로 사용 가능한 서버를 제한할 수 있다. 호스트 앱이 제공하는 연결 등 예외와 버전별 적용 범위를 검증해야 한다.
- [Claude Code 관리 설정 배포](https://code.claude.com/docs/en/managed-settings): 관리 설정은 시스템 파일·MDM 등으로 배포할 수 있다. 정책 저장 위치의 보호와 직원의 관리자 권한을 함께 검토한다.
- [Microsoft App Control 스크립트 강제](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/script-enforcement): 스크립트 통제는 호스트의 지원과 실제 강제 동작에 의존한다. 연동되지 않은 Python 등 인터프리터를 허용하면 그 내부 스크립트를 직접 통제하지 못할 수 있어 실행 파일 허용 목록만으로 충분하지 않다.
- [Apple Endpoint Security](https://developer.apple.com/documentation/endpointsecurity): 프로세스 실행 등을 사전 인가하거나 관찰하는 OS API가 있다. 전용 entitlement와 시스템 확장 배포가 필요하므로 일반 백그라운드 프로세스의 파일 감시와 같은 구현 범위로 산정하지 않는다. 지원 이벤트·성능·패키징은 대상 OS에서 검증한다.
- [OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/): 인젝션 대응은 단일 필터의 완전 차단 약속으로 다루지 않고 최소 권한과 사람의 검토 등을 함께 고려한다.
- [Agent Kit 제품 정의](agent-kit-definition.md), [ADR-005](../decisions/ADR-005-capability-evidence.md), [ADR-009](../decisions/ADR-009-execution-runtime-and-harness.md): 설정 배포 우선, 지원 증거, 선택 런타임의 기존 경계를 유지한다.

이 문서의 우선순위·부담·기대효과는 위 근거와 현재 저장소를 바탕으로 한 설계 판단이다. 구현 증명과 고객 검증 결과에 따라 갱신한다.
