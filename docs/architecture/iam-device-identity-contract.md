# IAM 기기 신원과 서비스별 OAuth/OIDC 연동 계약

- 결정일: 2026-09-25
- 상태: LM2-1 계약 확정(2026-09-25). 관리 채널의 상세 scope/claim·DPoP·등록/회수 기준은 [관리 인증 v1](daemon-management-auth-v1.md)을 따른다. [LM2-2 IAM 구현·로컬 검증](../reconstruction/phase-lm2-2-iam-device-identity.md)은 완료했다. [LM2-3 데몬 로컬 연동](../reconstruction/phase-lm2-3-daemon-auth.md)을 검증했으며 Gateway 연동은 LM2-4에 남는다.
- 적용 계획: [세 구성 요소 구현 계획](../product/three-component-implementation-plan.md), LM2 및 G-1A/G-2.

## 1. 결정과 책임

**IAM이 사용자·기기 신원과 기기 등록·키 바인딩·회수를 소유하고, 각 서비스는 필요한 기기 신원을 OAuth/OIDC의 scope·claim 계약으로 이용한다.** Gateway가 첫 소비자다. IAM을 사용하는 다른 서비스에 기기 등록을 일괄 요구하지 않으며, 추후 같은 계약을 도입할 수 있다. 독립형 Agent Kit의 로컬 자원 관리는 계속 IAM·Gateway 없이 동작한다.

| 구성 요소 | 소유하는 책임 |
|---|---|
| IAM | 등록 권한 확인, 테넌트·사용자와 기기의 관계, 공개키 등록·소유 증명·갱신·회수, 서비스별 허용 scope/claim과 토큰 발급 조건 |
| 서비스/Gateway | 대상 자원·행위에 필요한 인증 계약 선택, 액세스 토큰·요청 증명 검증, 최신 기기 상태 확인, 서비스·도구 권한 검사 |
| 데몬 | 기기 개인키 생성·보호, 등록 및 요청 증명, 로컬 정책 집행과 상태 보고 |
| Agent Kit | 로그인·조직/기기 등록 안내, 로컬 자원 관리와 상태 표시 |

기기 등록부를 Gateway에 복제하지 않는다. Gateway가 갖는 상태 캐시는 IAM의 신원·회수 기준을 소비하는 파생 데이터다. 정책 적용 상태와 관리 작업·감사는 Gateway/데몬의 책임이며, IAM의 등록 상태와 분리한다. `device=true`, `managed=false` 같은 클라이언트 제공 플래그를 신원이나 우회 허용의 근거로 사용하지 않는다.

## 2. 세 가지 계약

### A. 기기 등록·수명주기

1. 검증된 IAM 사용자·테넌트 및 조직의 등록 권한에 따라 등록을 시작한다. 요청 본문의 사용자·테넌트 값을 신원 근거로 삼지 않는다.
2. 데몬이 보호된 OS 저장소에 개인키를 생성하고 IAM에 공개키와 일회성 도전에 대한 소유 증명을 제출한다. IAM은 도전의 만료·재사용·등록 주체 바인딩을 검증한다.
3. IAM이 기기 식별자, 소속 관계, 검증된 공개키/키 버전, 등록·회수 상태를 관리한다. 개인키는 IAM·Gateway·AI 클라이언트나 Manifest에 전달하지 않는다.
4. 키 갱신·분실·재등록·회수 시 이전 키와 토큰의 처리, 승인 주체, 감사, 상태 전파 계약을 정의한다. 회수 상태를 새 로그인이나 refresh만으로 자동 복구하지 않는다.

기기 키의 소유 증명은 해당 키에 대한 증거다. 하드웨어에 묶인 비추출성이나 PC 전체 무결성을 보장한다고 표시하지 않는다. 하드웨어 증명은 필요할 경우 별도 지원·검증 항목으로 둔다.

### B. 서비스별 scope·claim과 토큰 발급

서비스별 계약은 기존 OAuth 클라이언트·보호 자원 설정에 연결해 버전으로 관리한다. 별도의 전역 '기기 인증 켜기' 플래그를 요구사항으로 추가하지 않는다. 각 계약은 아래 내용을 명시한다.

| 계약 항목 | 확정할 내용 |
|---|---|
| 소비자와 자원 | 등록 OAuth client, 대상 resource/audience, 사용자 위임 요청인지 데몬 관리 요청인지 |
| scope | 요청 가능·실제 부여 scope, 기기 신원 정보를 제공할 조건, 필요한 자원·행위 |
| claim | 이름·형식·의미·버전, 기기와 사용자/테넌트 관계, 누락·미지원 시 거부 규칙 |
| 증명 | 등록 기기 키와 토큰 결합, 요청별 소유 증명 방식, 지원 런타임 |
| 수명주기 | 토큰·증명·회수 캐시 수명, refresh 및 토큰 교환 시 유지할 바인딩, 폐기/재등록 처리 |

관리 채널은 `https://lynply.com/claims/device` 객체(`v`, `id`, `version`)를 확장 claim으로 확정했다. 구체적인 형식과 필수 조건은 [v1 스키마](daemon-management-auth-v1.md#4-액세스-토큰-스키마)를 따른다. OIDC 표준 claim이라고 표시하지 않으며, 기존 claim과의 충돌 및 서비스 간 불필요한 기기 추적을 고려해 식별자 노출 범위를 정한다. 개인키·원본 정책·필요 없는 단말 정보를 토큰에 넣지 않는다.

OIDC의 ID Token은 로그인 결과 확인에 사용한다. Gateway API와 관리 채널 인가에는 해당 자원을 audience로 하는 **액세스 토큰**을 사용한다. `claims` 요청 파라미터가 API 액세스 토큰의 필수 기기 정보를 자동 강제한다고 가정하지 않는다. JWT 액세스 토큰을 쓰는 경우 제공할 확장 claim과 수신 검증 규칙을 별도로 합의한다.

요청한 scope와 부여된 scope는 구분한다. **scope를 요청했다는 사실만으로 기기 증명에 성공한 것이 아니다.** IAM은 발급 계약을 검증하고, 서비스는 대상 자원의 필수 조건을 서버에서 강제한다. 기기 조건이 필요한 자원은 scope/claim 생략, 다른 클라이언트의 일반 토큰, Bearer로의 변경, refresh/토큰 교환을 통한 증명 제거로 접근할 수 없어야 한다. 기기 계약을 도입하지 않은 서비스는 기존 로그인·인가 계약을 유지한다.

### C. 액세스 토큰과 실제 요청의 키 소유 증명

LM2-1에서 데몬 관리 채널은 DPoP(RFC 9449), ES256/P-256으로 선택했다. mTLS(RFC 8705)는 인증서 수명주기·TLS 종단 신뢰 관리가 추가되므로 v1에서 제외했다. 임의 `X-Device-Id`나 독자 서명 헤더를 만들지 않는다. 이는 구현 기준의 선택이며, 관리 채널의 실제 상호운용 및 직접 MCP 클라이언트 지원 완료를 뜻하지 않는다.

- 관리 채널에서는 액세스 토큰의 `cnf.jkt`와 요청 proof의 공개키를 결합해 검증한다. **그 키가 IAM에 등록된 기기의 키인지, 또는 등록 기기가 허가한 별도 키인지도 검증 가능한 관계로 정의해야 한다.** 임의로 생성한 DPoP 키가 곧 등록 기기의 신원은 아니다.
- 선택한 방식에 따라 서명, 대상 메서드·URI, 토큰 결합, 시간·nonce 정책과 재생 방지, audience·issuer·테넌트·주체·scope를 검증한다. mTLS를 선택하면 TLS 종단과 인증서 결합의 신뢰 경계도 명시한다.
- 데몬→IAM 등록, 데몬→Gateway 관리, AI 클라이언트→Gateway `/mcp`를 각각 검증한다. 데몬의 관리 채널 증명은 AI 클라이언트의 별도 요청에 자동 전이되지 않는다.
- 데몬을 서명자로 사용해야 한다면 호출자·대상 audience·메서드/URI·토큰 바인딩·허용 작업을 제한하는 별도 계약을 먼저 검증한다. 임의 데이터를 서명해 주는 로컬 API나 개인키 전달로 클라이언트 지원 부족을 우회하지 않는다.
- JWT의 과거 등록 상태만으로 즉시 회수를 보장하지 않는다. IAM 회수 조회/이벤트, 서비스 캐시 및 토큰·키 갱신 규칙을 조합하고 허용 지연 상한을 정해 실제 거부 시점을 시험한다.

## 3. LM2 구현 순서와 완료 기준

| 순서 | 산출물 | 완료 기준 |
|---|---|---|
| LM2-1 계약 (확정) | 서비스별 scope·claim·발급 조건, 등록·갱신·회수, 관리 채널 증명 방식, 공통 fixture | [v1 상세 계약](daemon-management-auth-v1.md)·[공통 fixture](../contracts/daemon-management-v1/README.md) 확정. fixture 무결성 검증; 서비스 실제 거부 시험은 LM2-2~4에서 수행 |
| LM2-2 IAM (로컬 검증 완료) | 기기 등록부·키 소유 증명·회수, 계약에 따른 액세스 토큰 발급 | 다른 사용자/테넌트 등록, 만료/재사용 도전, 임의 키·회수 키·누락 증명 거부. 기존 인증 회귀 통과 |
| LM2-3 데몬 (로컬 검증) | 보호된 기기 키와 관리 채널 인증 어댑터 | IAM 등록, 등록 키와 토큰/요청 결합, 갱신·회수·재시작 시험. 키·자격 증명 비노출 |
| LM2-4 Gateway | 관리 채널 토큰/증명 검증, 상태 수신·중앙 조회 | 테넌트·기기 격리, scope 누락/다른 audience/잘못된 키/재생·중복 거부, 회수 전파, 단절 시 stale 표시 |

LM2는 관리 채널의 G-1A를 완료한다. **AI 클라이언트 직접 `/mcp` 요청의 기기 결합은 G-2에서 별도로 완료한다.** 직접 호출 클라이언트가 선택한 증명 방식을 지원하지 않으면 해당 기기 조건은 미지원으로 표시하고 경로/지원 범위를 재결정한다. 필수 기기 조건을 일반 Bearer로 낮춰 출시하지 않는다.

LM2 계약 시험에는 일반 로그인만 쓰는 서비스의 기존 동작 유지와 기기 조건이 필요한 자원의 우회 거부를 모두 포함한다. DPoP 자체, 등록 상태, 정책 준수 보고 중 하나만으로 전체 기기 신뢰를 판정하지 않는다.

## 4. 표준과 우리 확장의 구분

- [OIDC Core — 추가 claim](https://openid.net/specs/openid-connect-core-1_0.html#AdditionalClaims), [scope로 claim 요청](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims): 확장 가능한 인증 정보 전달 방식. 기기 등록·회수 API와 기기 claim 의미 전체를 규정하지 않는다.
- [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html): JWT 형식 OAuth 액세스 토큰 프로파일. 적용 여부와 기존 IAM 토큰 호환성은 계약 단계에서 확인한다.
- [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html): DPoP를 통한 토큰·요청의 키 소유 증명. 기기 등록이나 하드웨어 신뢰를 대신하지 않는다.
- [RFC 8705](https://www.rfc-editor.org/rfc/rfc8705.html): OAuth mTLS 클라이언트 인증 및 인증서 결합 액세스 토큰. 단순 TLS 사용과 구분한다.

현재 결정은 **표준 기반 확장 계약**이다. 기기 등록 수명주기, 기기 claim 의미, 서비스별 요구 조건과 회수 전파 규칙은 우리 시스템이 정의·검증해야 한다.
